1. Executive Summary

SANJEEVANI AI is designed as a clinical edge intelligence platform focused on emergency triage, patient monitoring, multimodal symptom detection, AI-assisted diagnosis, and proactive medical guidance. From the repository evidence, the project is a React-based front-end application with strong browser-side processing, a Convex backend for patient data persistence and auth, and a multi-module AI architecture that brings together:

  • Vision-based patient analysis using MediaPipe and TensorFlow.js
  • Audio-based distress and vocal pattern analysis
  • Care-plan generation and AI medical agent orchestration
  • Pharmacovigilance and drug-interaction analysis
  • Genomic and disease-risk scanning context
  • Epidemic monitoring and outbreak alert logic

In practical terms, the system behaves like a healthcare command center: a front-end patient intake and triage layer, a clinician dashboard, a multimodal AI analysis engine, and an underlying secure data layer. The system is architected to keep some sensitive patient processing local in the browser while pushing reasoning and retrieval tasks through AI APIs.

5. Startup and Runtime Flow

The app starts in the browser through src/main.jsx. It creates a Convex client and wraps the app in both the auth provider and convex provider.

import ReactDOM from 'react-dom/client'; import App from './App.jsx'; import { ConvexProvider, ConvexReactClient } from "convex/react"; import { AuthProvider } from './context/AuthContext'; const convex = new ConvexReactClient(import.meta.env.VITE_CONVEX_URL || "https://..."); ReactDOM.createRoot(document.getElementById('root')).render( <React.StrictMode> <ConvexProvider client={convex}> <AuthProvider> <App /> </AuthProvider> </ConvexProvider> </React.StrictMode> )

This means the front end is tightly integrated with a session-aware backend, not a static-only app. The frontend controls modules, receives user identity information, and loads patient records and AI outputs from Convex functions.

6. App-Level Control Flow

The primary orchestrator is src/App.jsx. It handles user authentication, side navigation, active module switching, triage queue state, outbreak alerts, patient follow-up scheduling, and feedback submission.

  • On initial load, it checks auth state and shows a login screen if not authenticated.
  • It stores triage queue items in React state as the patient is processed.
  • It invokes epidemic logic whenever a new triage case is submitted.
  • It uses route-like module state to switch UI between emergency triage, records, pharma, vision, multi-agent AI, etc.
  • It supports a feedback modal that pushes developer feedback into the Convex backend.

8. Core Clinical Intelligence Flow

The true system is not just a dashboard; it is a multimodal interpretation system. The README and component names suggest that several engines work in parallel before a patient is classified or a recommendation is formed:

  1. Patient enters symptoms or receives a triage assessment.
  2. Browser captures images/audio/speech context via camera and microphone APIs.
  3. Facial landmarks and vocal features are transformed into quantitative stress, pain, or distress scores.
  4. These scores are fused into a multimodal patient state representation.
  5. AI agents determine which specialists are relevant to the case.
  6. Generated outputs are structured as clinical notes, recommendations, and risk flags.

9. Vision Layer and Computer Vision

This project depends heavily on face-based and motion-based sensing. The package includes face detection and face mesh libs, plus MediaPipe face detection and TF.js models. The architecture points clearly to two major vision styles:

  • Face landmark extraction for emotion, stress, and pain inference

The README specifically calls out rPPG (remote photoplethysmography), facial distress detection, and touchless vital estimation. This is a strong signal that the project tries to estimate physiology from visual signals alone rather than relying on raw clinical devices.

19. Risks and Real-World Constraints

While the architecture is impressive, real-world medical deployments require much more than a demo-grade stack. The main risks include:

  • Model accuracy and confidence calibration in sensitive clinical contexts
  • Need for formal data governance and patient consent flows
  • Risk of incorrect AI inference without clinician supervision
  • Need for valid medical-grade validation tests and clinical review
  • Privacy and compliance issues around camera/audio processing

In other words, the project is conceptually solid and well-structured, but production deployment in a regulated healthcare setting would require deeper legal, clinical, and engineering validation.

20. Recommended Production Hardening Roadmap

  1. Separate clinical decision support from raw inference and enforce human review.
  2. Add strict data retention policies for audio, video, and patient data.
  3. Implement audit logs and secure event tracking across all modules.
  4. Introduce confidence thresholds and fallback workflows when AI confidence is low.
  5. Harden the backend with RBAC, access control, and environment validation.
  6. Create model versioning and dataset drift monitoring for all inference components.
  7. Integrate hospital EHR APIs or a secure clinical data exchange layer.
